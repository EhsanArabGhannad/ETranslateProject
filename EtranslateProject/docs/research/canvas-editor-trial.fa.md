# نتیجهٔ آزمایش عملی Canvas Editor

تاریخ: ۲۰۲۶-۱۰-۲۰

## جمع‌بندی تصمیم

Canvas Editor نسخهٔ npm `1.0.5` در نمونهٔ مستقل اجرا و آزمایش شد. **در وضعیت فعلی برای ادیتور ترجمهٔ چندزبانهٔ محصول تأیید نمی‌شود.** صفحه‌بندی، تایپ، تاریخچه و نمونه‌های جدول پیش رفتند؛ اما اتصال ظاهری حروف فارسی کافی نبود: مختصات مکان‌نما ترتیب چپ‌به‌راست داشت و متن مخلوط با مرجع طبیعی مرورگر تفاوت نشان داد. خروجی هم نیازمند حل مسئلهٔ وفاداری چاپ در کنار متن قابل‌جست‌وجو است.

این حکم دربارهٔ همین نسخه، تنظیم و نمونه‌هاست، نه همهٔ امکانات آیندهٔ کتابخانه یا همهٔ گزینه‌های رایگان. ادیتور، قرارداد ذخیره، renderer و دیتابیس محصول تغییر نکردند. [اجرای نمونه](../../experiments/canvas-editor-trial/README.fa.md)

## محیط و مرز بررسی

- یک بستهٔ MIT با نسخهٔ دقیق و integrity در lockfile؛ اسکریپت نصب اجرا نشد. اجرای نهایی با Node `24.19.0` بود؛ Node سراسری دستگاه تغییر نکرد.
- استفاده از فونت‌های Noto موجود، A4 و حاشیه‌های مشخص؛ wrap روی `break-word`. دادهٔ واقعی، سرویس خارجی، حساب یا لایسنس تجاری استفاده نشد.
- یک baseline تاریخچه با API رسمی ثبت شد؛ بدون آن، افزودن برنامه‌ای پیش از اولین تعامل مکان‌نما baseline مناسبی برای Undo نداشت. این آماده‌سازی میزبان است؛ سورس vendor تغییر نکرد.
- RTL/BiDi به‌صورت ظاهری و با اندازه‌گیری public cursor API بررسی شد؛ تضمین پوشش همهٔ ترکیب‌های زبان، اعداد، selection و فونت نداریم.
- Clipboard واقعی Word، DOCX واقعی، شاخهٔ مستقل PDF، قالب‌های واقعی، تصاویر خصوصی، امضا و API ذخیره در این بررسی نیستند. مواردی که به دروازهٔ RTL/چاپ وابسته‌اند بی‌دلیل وارد محصول نشده‌اند.

## نتایج مشاهده‌شده

| آزمون | نتیجهٔ محلی |
| --- | --- |
| تایپ فارسی/لاتین | ورود با صفحه‌کلید در متن فارسی و Undo/Redo پاس شد؛ snapshot داده بازگشت. این، صحت جانمایی مکان‌نما در RTL را ثابت نمی‌کند. |
| حروف و نویسه‌ها | حروف فارسی متصل دیده شدند؛ فارسی، حروف ویژهٔ ترکی و نیم‌فاصله در داده حفظ شدند. متن مخلوط، ترتیب و فاصلهٔ نامناسب نسبت به مرجع طبیعی مرورگر نشان داد. |
| مکان‌نما در «سلام» | سه مختصات متوالی API برای حروف منطقی: حدود `609.97 → 629.43 → 636.10`؛ x افزایش داشت، نه حرکت متناظر راست‌به‌چپ. همراه با مشاهدهٔ متن مخلوط، این مانع تأیید RTL است. |
| متن ۴۸ پاراگرافی | ۴ صفحه و ۴۸ نشانگر متن حفظ شدند. پرش به صفحهٔ دوم، JSON را تغییر نداد. |
| جریان متن و بازخوانی | افزودن ۴۰ پاراگراف، تعداد را از ۴ به ۷ رساند؛ Undo داده و تعداد ۴ صفحه را برگرداند. round-trip بومی در حافظهٔ تب پاس شد؛ ذخیرهٔ پایدار آزمایش نشده است. |
| Zoom و عرض باریک | ۷۵/۱۰۰/۱۲۵ درصد تعداد ۴ صفحه و داده را حفظ کردند؛ در عرض ۳۹۰ پیکسل، اسکرول کاغذ داخلی بود. اعتبارسنجی جامع مکان‌نما در zoom ادعا نمی‌شود. |
| جدول ۴۶ ردیفی | ۴ صفحه؛ متن، هر ۴۶ شناسهٔ ردیف و نشانگر بعد از جدول در عملیات واقعی رسم دیده شدند. تکرار سربرگ و تمام ترکیب‌های ادغام هنوز تأیید جامع نشده‌اند. |
| سلول ادغام‌شده | یک صفحه و نمایش اولیهٔ rowspan همراه با نشانگر انتهایی؛ برخلاف اتصال مستقیم به محصول، فقط schema بومی خود کتابخانه استفاده شده است. |
| سلول بلند | ۳ صفحه، بدون رشد بی‌رویه در همین نمونه؛ نشانگر انتها و متن بعد از جدول واقعاً رسم شدند و داده حذف نشد. |
| پاراگراف بلند | ۵ صفحه؛ نشانگر انتهایی رسم و متن حفظ شد. این حالت را با PDF متن عادی یکی نمی‌گیریم. |
| HTML قالب‌دار ثابت | اندازه، رنگ، تراز مرکزی، bold/italic و بخشی از هایلایت در JSON بومی دیده شدند؛ `font: Arial` در خروجی نیامد. فاصلهٔ خطوط و حفظ کامل هایلایت روی تمام runها تأیید نیست. این آزمون Word واقعی نیست. |
| مدل ذخیره | JSON بومی شامل `header/main/footer` است و validator فعلی محصول آن را رد می‌کند. این تفاوت قابل انتظار بین موتورهاست و نیازمند adapter/نسخه‌بندی است؛ به‌تنهایی نقص Canvas نیست. |

در نسخهٔ نصب‌شده، راه‌اندازی context رسم در سورس `direction = "ltr"` دارد و نمونهٔ رسم متن مخلوط نیز `ltr` ثبت کرد. استنباط ما از اندازه‌گیری و تصویر، نبود پشتیبانی قابل اتکای RTL در این پیکربندی است؛ با «راست‌چین» یا معکوس‌کردن رشته این مسئله را حل‌شده اعلام نمی‌کنیم.

## دو مسیر خروجی، دو نتیجهٔ متفاوت

### ۱. تصویر صفحات در PDF

از API رسمی `getImage` در حالت Print، چهار PNG گرفته و برای آزمون در چهار صفحهٔ A4 یک PDF قرار داده شد. این همان PDF آرشیوی محصول یا یک SDK مستقل PDF نیست. مسیر `executePrint` نسخهٔ نصب‌شده نیز در سورس از تصویر صفحات استفاده می‌کند، ولی خود دیالوگ چاپ سیستم در آزمون باز نشد.

بررسی pypdf: **۴ صفحه، ۴ تصویر و صفر نویسهٔ قابل‌استخراج**. ظاهر صفحه‌ها از رندر Canvas می‌آید، اما این مسیر متن قابل‌جست‌وجو/انتخاب، دسترس‌پذیری یا کیفیت vector را فراهم نکرد. برای ترجمهٔ رسمی، این مبنای پذیرش خروجی نهایی ما نیست؛ ادعای ممنوعیت حقوقی PDF تصویری هم نمی‌کنیم.

### ۲. HTML صادرشده در Chromium

HTML متن بومی با فونت محلی و کاغذ A4 در یک صفحهٔ آزمایش جدا به PDF تبدیل شد. متن هر ۴۸ نشانگر قابل‌استخراج بود؛ اما به‌جای ۴ صفحهٔ Canvas، **۳ صفحه** ایجاد شد. هشت نشانگر در صفحهٔ دیگری قرار گرفتند:

| نشانگر | Canvas | PDF از HTML |
| --- | --- | --- |
| `MARK_016` | ۲ | ۱ |
| `MARK_030` تا `MARK_032` | ۳ | ۲ |
| `MARK_045` تا `MARK_048` | ۴ | ۳ |

این مسیر را میزبان آزمایش از HTML ساخته، نه یک موتور PDF اختصاصی vendor. سربرگ/پابرگ واقعی محصول و قانون صفحهٔ آخر به آن اضافه نشده‌اند. نتیجه فقط اثبات می‌کند مسیر سادهٔ موجود، تطابق چاپ را خودبه‌خود نمی‌دهد؛ ناممکن‌بودن ساخت مسیر بهتر را ثابت نمی‌کند. PDFها خروجی میانی QA هستند و برای مشتری/امضا تحویل داده نمی‌شوند.

## آزمون و امنیت

۴ آزمون fixture، یک آزمون مرورگر و مقایسهٔ دو مسیر PDF اجرا شدند. حفظ داده، تایپ، history، round-trip، markerهای صفحه و رسم انتهای جدول/سلول کنترل شدند. **پاس شدن harness به معنی تأیید کیفیت موتور نیست**؛ شاخص‌های RTL و چاپ همچنان عدم تأیید را ثبت می‌کنند.

۵۰۸ آزمون عادی .NET و ۴۵ آزمون JavaScript قبلی نیز پاس شدند؛ opt-inهای محیطی در اجرای عادی skip ماندند. گزارش توسعه و تصاویر در `tmp/canvas-editor-trial` هستند؛ `browser-report.json` و `export-comparison.json` نتایج ماشین‌خوان‌اند. خروجی قدیمی یک اجرای ناموفق را نتیجهٔ اجرای فعلی حساب نکنید.

سرور فقط روی loopback با فهرست فایل‌های مشخص، GET/HEAD و بدون POST است. در آزمون هیچ درخواست HTTP خارجی ثبت نشد؛ clipboard/drop/context menu عمومی برای این محیط مسدود است. CSP آزمایش، style درون‌صفحه‌ای، تصویر `data:` و worker باندل‌شدهٔ `blob:` را برای کتابخانه اجازه می‌دهد؛ CSP محصول تغییر نکرده است. پیش از محصول، ممیزی امنیت، مجوز و دسترس‌پذیری جداگانه لازم است؛ قابلیت دسترس‌پذیری خود SDK در این آزمایش خاموش بود و تأیید نشده است.

## قدم بعدی پیشنهادی

پس از دو نمونهٔ رایگان، هیچ‌کدام را آمادهٔ اتصال به محصول نمی‌نامیم. پیشنهاد مهندسی: **ارزیابی آزمایشی Syncfusion با همان آزمون‌های RTL، جدول و PDF، پیش از خرید و تغییر schema**. هنوز نصب یا آزمایش نشده و هیچ کیفیتی برای آن تضمین نمی‌کنیم؛ دسترسی ارزیابی باید از مسیر مجاز کاربر فراهم شود و کلید نباید وارد کد یا چت شود.

اگر انتخاب نهایی «بدون هزینهٔ لایسنس» باشد، مسیر جایگزین یک مرحلهٔ مهندسی مشخص روی Tiptap است: رفع مشکل سلول بلند، هماهنگی layout و PDF و قرارداد نسخه‌دار جدول. این کار از نصب یک افزونه بیشتر است و باید جداگانه برآورد و تصویب شود. تغییر schema قبل از انتخاب موتور، تبدیل آرشیو درجا، یا تعویض خودکار renderer انجام نمی‌شود.
