# راهنمای پیش‌سفارش اشتراک با لیر

این مرحله فقط ثبت و لغو **پیش‌سفارش بدون پرداخت** را اضافه می‌کند. درگاه انتخاب نشده و قیمت پلن‌ها مشخص نیست. هیچ پولی دریافت نمی‌شود؛ ثبت، انقضا یا لغو پیش‌سفارش اشتراک را فعال، تمدید یا لغو نمی‌کند.

## تست دستی، مورد به مورد

1. پروژه را اجرا کنید و با حساب مالک یا مدیر یک فضای کاری وارد شوید.
2. از صفحهٔ «وضعیت اشتراک»، لینک «پیش‌سفارش خرید یا تمدید» را باز کنید. آدرس مستقیم: `/PurchaseOrders?tenantId=<شناسهٔ فضای کاری>`.
3. ارز باید «لیر ترکیه · TRY» باشد. دارالترجمه پلن دارالترجمه و مترجم مستقل پلن مستقل را می‌بیند.
4. با تنظیمات پیش‌فرض، قیمت «هنوز تعیین نشده» است؛ این به معنی صفر یا رایگان نیست. دکمه فقط پیش‌سفارش بدون پرداخت ثبت می‌کند.
5. ثبت کنید؛ شناسه، نام پلن، تعداد ماه، مبلغ نامشخص، زمان ایجاد و پایان اعتبار در تاریخچه ظاهر می‌شوند. پیام باید صریحاً بگوید پرداختی انجام نشده است.
6. وضعیت و تاریخ‌های اشتراک را قبل و بعد مقایسه کنید؛ نباید تغییر کنند. فضای کاری منقضی همچنان فقط‌خواندنی می‌ماند، ولی مالک/مدیر می‌تواند پیش‌سفارش ثبت کند.
7. بازآوری صفحه نباید زمان اعتبار پیش‌سفارش را تمدید کند. اعتبار دقیقاً ۳۰ دقیقه است؛ بعد از پایان، وضعیت منقضی و دکمهٔ لغو حذف می‌شود.
8. یک پیش‌سفارش باز را لغو کنید؛ فقط وضعیت همان پیش‌سفارش تغییر می‌کند. اشتراک، مدارک و تاریخچه حفظ می‌شوند.
9. با نقش Translator یا Reviewer، صفحهٔ پیش‌سفارش باید 403 بدهد؛ صفحهٔ معمول وضعیت اشتراک همچنان قابل مشاهده است. کاربر غیرعضو نباید اطلاعات فضای کاری را ببیند.

این صفحه ۵۰ پیش‌سفارش اخیر را نشان می‌دهد. ایجاد چند پیش‌سفارش با شناسه‌های درخواست جدید ممکن است؛ محدودیت تعداد و سیاست یک پیش‌سفارش باز هنوز پیاده نشده‌اند. پیش‌سفارش رسید، فاکتور یا اثبات پرداخت نیست.

## تنظیم قیمت، وقتی تصمیم گرفته شد

در `src/Services/Billing/ETranslate.Billing.Api/appsettings.json`، هر عضو `SubscriptionPlans:Plans` فیلد `PriceTry` دارد. فعلاً هر دو `null` هستند. پس از تصمیم تجاری، مبلغ مثبت با حداکثر دو رقم اعشار وارد و Billing را دوباره اجرا کنید. صفر، منفی، اعشار بیشتر و مبلغ خارج از ظرفیت `decimal(18,2)` رد می‌شوند.

مبلغ برای **کل تعداد ماه همان پروفایل** است، نه قیمت هر کاربر یا مبلغی که دوباره در تعداد ماه ضرب شود. ماه تقویمی میلادی در UTC محاسبه می‌شود؛ دورهٔ آزمایشی همچنان ۳۰ روز است. مالیات، فاکتور و شرایط تجاری هنوز تعریف نشده‌اند.

حتی با تعیین قیمت، پرداخت غیرفعال است. پیش‌سفارش قدیمی مبلغ و مدت خودش را نگه می‌دارد؛ تنظیم قیمت، پیش‌سفارش نامشخص قدیمی را قابل پرداخت نمی‌کند. نوع مشتری برای نمایش پلن از عضویت زندهٔ Identity می‌آید؛ رکورد قدیمی Billing با نوع نامشخص، صرفاً با ثبت پیش‌سفارش تطبیق یا فعال نمی‌شود.

## اجرا و Migration

از پوشهٔ Solution:

```powershell
dotnet build ETranslate.slnx
dotnet run --project src/Orchestration/ETranslate.AppHost/ETranslate.AppHost.csproj
```

Migration `AddSubscriptionPurchaseOrders` هنگام راه‌اندازی Billing اعمال می‌شود؛ فقط جدول پیش‌سفارش را اضافه می‌کند. SQL Server بومی فعلی کافی است؛ Docker و WSL لازم نیست. در محیط واقعی پشتیبان‌گیری و برنامهٔ استقرار لازم است. Down جدول و تاریخچهٔ پیش‌سفارش را حذف می‌کند و برگشت امن داده‌ای نیست.

## تست خودکار

```powershell
dotnet test ETranslate.slnx
```

با AppHost و SQL Server محلی روشن، در PowerShell 7:

```powershell
./tests/ETranslate.EndToEndTests/Verify-PurchaseOrders.ps1
```

اسکریپت فقط آدرس‌های loopback می‌پذیرد. تست‌های قبلی امضا، تیم، محدودسازی و دورهٔ پولی را نیز اجرا می‌کند؛ سپس پیش‌سفارش، تکرار و هم‌زمانی، مبلغ/ارز جعلی، جداسازی فضاها، تغییر نقش زنده، انقضا، فرم وب، CSRF و عدم تغییر اشتراک را بررسی می‌کند. چهار تست SQL جدید هم اجرا می‌شوند. هیچ پرداخت یا درگاه واقعی استفاده نمی‌شود. بررسی وب، عملکرد و HTML است؛ تست ظاهری در مرورگر نیست.

فقط داده‌های ساختگی تازهٔ همان اجرا ایجاد می‌شوند و باقی می‌مانند. برای شبیه‌سازی انقضا، تاریخ‌های یک پیش‌سفارش تازه با SQL به گذشته می‌روند؛ ساعت سیستم یا دادهٔ واقعی تغییر نمی‌کند. تست‌های قبلی نیز بازهٔ اشتراک ساختگی خودشان را تغییر می‌دهند. **فقط توسعهٔ محلی؛ روی محیط واقعی اجرا نکنید.**

برای چهار تست SQL به‌تنهایی، پس از اعمال Migration روی `.\ESIMSSQLSERVER`:

```powershell
$env:ETRANSLATE_BILLING_SQL_TESTS = '1'
dotnet test tests/ETranslate.DomainTests/ETranslate.DomainTests.csproj --filter 'FullyQualifiedName~PurchaseOrderSqlTests'
Remove-Item Env:ETRANSLATE_BILLING_SQL_TESTS
```

## API

همهٔ مسیرهای سفارش به توکن معتبر و عضویت فعال Owner/Administrator نیاز دارند:

```text
GET  /api/v1/tenants/{tenantId}/subscription/orders
GET  /api/v1/tenants/{tenantId}/subscription/orders/{orderId}
POST /api/v1/tenants/{tenantId}/subscription/orders
POST /api/v1/tenants/{tenantId}/subscription/orders/{orderId}/cancel
```

بدنهٔ ایجاد فقط `planCode` و `requestId` با UUID غیرخالی است؛ بدنهٔ لغو فقط `expectedVersion` است. مبلغ، ارز، وضعیت و شناسهٔ پرداخت از کاربر پذیرفته نمی‌شوند. ایجاد اولیه 201 و تکرار معتبر 200 می‌دهد. همان شناسهٔ درخواست به فضای کاری، ایجادکننده و پلن اصلی مقید است؛ تغییر ایجادکننده یا پلن با آن 409 می‌دهد. تکرار پس از لغو/انقضا همان پیش‌سفارش را برمی‌گرداند، نه سفارش تازه یا اعتبار طولانی‌تر. لغو منقضی یا نسخهٔ قدیمی 409 است. نقش غیرمدیر 403 و سفارش فضای دیگر 404 است.

گام پرداخت واقعی، بعد از تعیین قیمت‌ها و انتخاب درگاه است. آن مرحله باید اصالت پرداخت نهایی و تطابق مبلغ، TRY، سفارش و مالکیت را سمت سرور تأیید کند؛ هیچ دادهٔ برگشتی مرورگر یا شناسهٔ متنی به‌تنهایی اشتراک را فعال نمی‌کند.
