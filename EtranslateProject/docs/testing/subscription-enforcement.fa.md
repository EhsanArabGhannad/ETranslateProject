# راهنمای تست محدودسازی اشتراک

این قدم قواعد اشتراک را روی سرویس‌ها اعمال می‌کند؛ پرداخت و تمدید آنلاین هنوز ساخته نشده‌اند. هیچ فایل یا ترجمه‌ای پس از انقضا حذف نمی‌شود.

## قواعد فعلی

| وضعیت | عملیات جدید یا تغییر | اسناد موجود و سابقه |
|---|---|---|
| دورهٔ آزمایشی معتبر / Active معتبر | طبق نقش و مجوز عضو | قابل مشاهده و دانلود |
| Expired / PastDue / Canceled | متوقف؛ پاسخ ۴۰۲ | قابل مشاهده و دانلود |
| Pending | موقتاً متوقف؛ پاسخ ۵۰۳ | قابل مشاهده و دانلود |
| خطای بررسی اشتراک | موقتاً متوقف؛ پاسخ ۵۰۳؛ نه انقضای ساختگی | قابل مشاهده و دانلود |

منظور از «قابل مشاهده» فقط عضو فعال و مجاز همان فضای کاری است؛ انقضا مجوز عمومی برای فایل‌ها نمی‌سازد. اشتراک معتبر هم مجوز نقش کاربر را افزایش نمی‌دهد.

## چه چیزهایی محدود می‌شوند؟

- ساخت و تغییر پرونده و تخصیص مترجم.
- ساخت سند، اتصال قالب و ذخیرهٔ نسخهٔ جدید متن.
- ساخت یا تغییر قالب، وضعیت قالب و آپلود لوگو.
- آپلود مدرک مبدأ، تولید PDF و تولید یا بازاستفادهٔ پیش‌نمایش از مسیر POST.
- ارسال و تصمیم بازبینی، بازگشایی یا پس‌گرفتن آن.
- آماده‌سازی و لغو برنامهٔ امضا. امضای واقعی همچنان پیاده‌سازی نشده است.

ورود و خروج، صفحهٔ اشتراک، مدیریت اعضا، خواندن تاریخچه و دانلود فایل‌های قبلاً ذخیره‌شده محدود نمی‌شوند. مالک و مدیر هم از قواعد اشتراک معاف نیستند.

## تست دستی

1. AppHost را اجرا کنید و وارد یک فضای کاری با آزمایشی معتبر شوید. ایجاد و ذخیرهٔ ترجمه طبق نقش قبلی باید کار کند.
2. برای نمونهٔ منقضی‌شده، از تست محلی زیر استفاده کنید؛ تاریخ اشتراک واقعی را برای آزمایش تغییر ندهید.
3. فضای کاری نمونهٔ منقضی‌شده را باز کنید. پیام «فقط‌خواندنی» و لینک بررسی اشتراک باید دیده شود؛ کنترل‌های ساخت پرونده و قالب غیرفعال‌اند.
4. یک ترجمهٔ موجود را باز کنید. ویرایش و ذخیره و تولید فایل جدید متوقف است، اما متن، نسخه‌های قبلی، مدارک مبدأ و PDFهای قبلی قابل مشاهده/دانلودند. لینک دانلود پیش‌نمایش‌های تاریخی هم باقی می‌ماند.
5. صفحهٔ امضا و تخصیص را باز کنید. سابقه باقی است، اما فرم‌های تغییر درخواست یا تخصیص نمایش داده نمی‌شوند.
6. مدیریت اعضا را باز کنید. تغییر مجاز نقش یا فعال/غیرفعال‌کردن عضو همچنان ممکن است؛ دسترسی عضو غیرفعال به اسناد هم قطع می‌شود.
7. اگر صفحهٔ ویرایش پیش از انقضا باز بوده، درخواست ذخیره پس از انقضا باید رد شود. متن ذخیره‌نشده برای کپی در پاسخ صفحه حفظ می‌شود؛ پیام موفقیت ذخیره نباید نمایش داده شود. قبل از بازآوری یا ترک صفحه از متن کپی بگیرید.
8. برای خطای اتصال، فقط در محیط توسعه Billing را موقتاً متوقف کنید. مشاهدهٔ فضای کاری و دانلودهای قبلی باید ممکن بماند؛ عملیات تغییر باید با پیام «قابل بررسی نیست» رد شود، نه پیام انقضای ساختگی. پس از تست سرویس را دوباره اجرا کنید. بررسی وضعیت برای نمایش صفحه حداکثر چهار ثانیه بودجه دارد؛ زمان کل بعضی عملیات با بررسی‌های دیگر می‌تواند بیشتر باشد.
9. دوره دقیقاً ۳۰ روز است و در لحظهٔ پایان مسدود می‌شود؛ منتظر اجرای کارگر انقضا نمی‌مانیم. عملیات از قبل مجازشده و در حال اجرا ممکن است پس از پایان تمام شود؛ این سیستم قفل تراکنشی مشترک بین سرویس‌ها نیست.

## تست خودکار

PowerShell 7، AppHost روشن و SQL Server توسعهٔ محلی لازم است:

```powershell
./tests/ETranslate.EndToEndTests/Verify-SubscriptionEnforcement.ps1
```

این تست ابتدا تست‌های موجود فضای کاری، تیم، آماده‌سازی امضا و پیش‌نمایش را اجرا می‌کند؛ سپس تمام مسیرهای فعلی تغییر، آپلودها، درخواست مستقیم به API، حفظ فایل‌ها و متن ذخیره‌نشده، مترجم مستقل و دارالترجمه را بررسی می‌کند.

فقط آدرس‌های HTTP/HTTPS محلی پذیرفته می‌شوند. با `sqlcmd` در `.\ESIMSSQLSERVER` و دیتابیس `ETranslateBilling` فقط اشتراک دو فضای کاری ساختگیِ ایجادشده در همان اجرا تغییر می‌کند. تاریخ انقضا و حالت‌های PastDue/Canceled/Active/بازگشت آزمایشی صرفاً نمونهٔ تست‌اند؛ این‌ها API پرداخت یا تمدید محصول نیستند. داده‌ها و نمونه‌های منقضی‌شده باقی می‌مانند و هیچ سندی پاک نمی‌شود. روی محیط واقعی اجرا نکنید.

برای دریافت مشخصات حساب ساختگی همان اجرای تست می‌توانید `-EmitTestFixture` اضافه کنید؛ خروجی آن رمز حساب تست را دارد و نباید با دادهٔ واقعی یا در خروجی عمومی منتشر شود.

```powershell
dotnet test ETranslate.slnx
```

تست‌های واحد، خطای اتصال و پاسخ نامعتبر، Pending، مرز زمانی، عدم اجرای عملیات ردشده و حفظ متن را بدون تغییر ساعت سیستم یا دادهٔ واقعی بررسی می‌کنند. هیچ Migration جدیدی برای این قدم لازم نیست.

## پاسخ‌های محدودسازی

درخواست تغییر ردشده، یک کد مشخص دارد:

- `402 / subscription_required`: اشتراک معتبر لازم است؛ به‌معنای انجام پرداخت یا وجود درگاه فعال نیست.
- `503 / subscription_pending`: ایجاد خودکار اشتراک هنوز تکمیل نشده است.
- `503 / subscription_unavailable`: وضعیت قابل تأیید نیست؛ تغییرات موقتاً متوقف‌اند.
- `401 / 403`: مشکل ورود یا عضویت؛ با اشتراک اشتباه نشود.

مسیر خواندن تصمیم، `GET /api/v1/tenants/{tenantId}/subscription/write-access` در Billing، توکن عضو فعال می‌خواهد. پاسخ مشاهدهٔ موفق آن حتی برای حالت ممنوع ۲۰۰ است و `canWrite=false` و دلیل دارد؛ خودِ درخواست تغییر است که ۴۰۲ یا ۵۰۳ می‌گیرد. این پاسخ توکن مجوز قابل‌استفادهٔ مجدد نیست؛ هر تغییر دوباره بررسی می‌شود. سرویس‌ها دیتابیس یکدیگر را نمی‌خوانند و غیرفعال‌کردن دکمه‌ها تنها لایهٔ حفاظت نیست.
