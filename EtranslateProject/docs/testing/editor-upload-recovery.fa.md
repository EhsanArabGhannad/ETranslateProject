# راهنمای آپلود، تلاش دوباره و تداخل درخواست‌ها

تاریخ: ۲۰۲۶-۱۱-۰۲

آپلود فایل مبدا و تصویر بدنه اکنون در همان صفحه قابل تلاش دوباره است، بدون اینکه گم‌شدن پاسخ باعث ایجاد فایل تکراری شود. این قابلیت برای **همان فایل انتخاب‌شده** است؛ انتخاب مجدد یا بازآوری صفحه، عملیات تازه‌ای شروع می‌کند.

## رفتار قابل تست در برنامه

۱. فایل مبدا را انتخاب و بارگذاری کنید. هنگام ارسال، تایپ، ذخیره و ارسال بازبینی موقتاً متوقف می‌شوند؛ متن فعلی و تاریخچهٔ ویرایش حفظ می‌شوند. پس از پاسخ معتبر یا خطای موقت، امکان ادامه برمی‌گردد.

۲. اگر نتیجهٔ آپلود مشخص نشد، پیام ترکی می‌گوید ممکن است فایل در سرور ثبت شده باشد. **فایل را دوباره انتخاب نکنید؛ با همان انتخاب، دوباره دکمهٔ بارگذاری را بزنید.** سرور فایل ثبت‌شدهٔ همان عملیات را برمی‌گرداند؛ فایل و ردیف فهرست اضافه ساخته نمی‌شود.

۳. برای تصویر داخل ترجمه نیز همین قاعده برقرار است. اگر خود تصویر پس از آپلود باز نشود، تلاش دوباره از همان فایل ثبت‌شده استفاده می‌کند و تصویر فقط پس از دریافت و نمایش معتبر وارد متن می‌شود. درج تصویر همچنان تغییر ذخیره‌نشده است و باید نسخهٔ ترجمه را ذخیره کنید.

۴. آپلود مبدا حداکثر ۴۵ ثانیه برای دریافت پاسخ و اطلاعات فایل منتظر می‌ماند؛ تصویر هم مهلت موجود ۴۵ثانیه‌ای شامل دریافت/بازکردن تصویر را دارد. لغو انتظار اثبات نمی‌کند که سرور چیزی ثبت نکرده است؛ تکرار خودکار انجام نمی‌شود.

۵. خطای قطعیِ تعارض نسخه/بازبینی یا رد دسترسی، تایپ و ذخیره را قفل نگه می‌دارد. متن محلی باقی می‌ماند؛ وضعیت جدید را در تب جدا بررسی کنید. خطای موقت سرویس و قطع اتصال، موفقیت اعلام نمی‌کنند.

۶. پس از دریافت اطلاعات فایل مبدا، آپلود تمام است؛ انتظار پیش‌نمایش PDF مانع ادامهٔ کار نمی‌شود. قواعد PDF همچنان بر نسخهٔ ذخیره‌شده تکیه دارند.

## اجرای خودکار

از ریشهٔ راه‌حل با PowerShell 7:

```powershell
./tests/ETranslate.EndToEndTests/Verify-EditorUploads.ps1
dotnet test ETranslate.slnx --no-restore -v quiet
```

پیش‌نیاز: SQL Server محلی `.\ESIMSSQLSERVER`، مجوز ساخت دیتابیس آزمایشی، .NET 10، وابستگی‌های محلی کلاینت و مرورگر Playwright در مسیر تست‌های قبلی. دانلود و نصب خودکار انجام نمی‌شود. اسکریپت AppHost یا دیتابیس فعلی را اجرا نمی‌کند؛ شش سرویس واقعی، شش دیتابیس تازه و مرورگر مستقل ساخته و همان منابع پاک می‌شوند.

## دوازده سناریوی واقعی

| سناریو | انتظار |
|---|---|
| قطع اتصال پیش از آپلود مبدا | تغییری ثبت نشود؛ تلاش دستی یک فایل بسازد |
| گم‌شدن پاسخ مبدا پس از ثبت | تلاش دوباره همان فایل را برگرداند |
| گم‌شدن پاسخ تصویر پس از ثبت | یک تصویر مدیریتی در سرور و یک درج در ادیتور |
| شکست دریافت تصویر خصوصی | تلاش دوباره فایل دیگری نسازد |
| انتظار طولانی مبدا | مهلت تمام شود، متن بماند، ارسال تکراری/ذخیره/بازبینی/تصویر هم‌زمان وارد نشوند |
| دو آپلود هم‌زمان مبدا با یک شناسه | پاسخ‌های ۲۰۱ و ۲۰۰، فقط یک فایل و رکورد |
| دو آپلود هم‌زمان تصویر با یک شناسه | پاسخ‌های ۲۰۱ و ۲۰۰، فقط یک فایل و رکورد |
| استفادهٔ نادرست از شناسه | بایت متفاوت با نام/اندازهٔ یکسان و پروندهٔ دیگر رد شوند؛ درخواست بی‌نشست مجاز نباشد |
| آپلود مبدا هم‌زمان با ذخیره | وضعیت نهایی معتبر و فایل‌ها/نسخه‌ها سازگار بمانند |
| آپلود مبدا هم‌زمان با بازبینی | در صورت موفقیت هر دو، فایل در فهرست تثبیت‌شدهٔ بازبینی باشد |
| آپلود تصویر هم‌زمان با ذخیره | نسخه و تصویر معتبر بمانند؛ فایل درخواست ردشده باقی نماند |
| آپلود تصویر هم‌زمان با بازبینی | قفل حفظ شود و پس از ثبت بازبینی آپلود دیگری پذیرفته نشود |

چهار جفت HTTP واقعاً هم‌زمان ارسال می‌شوند، اما اجبار نمی‌کنیم هر دو handler هم‌زمان یک rowversion قدیمی بخوانند. ممکن است هر دو در ترتیب معتبر موفق شوند. نتیجهٔ آزمون، کنترل وضعیت نهایی و ترتیب مجاز است، نه ادعای اینکه همیشه فقط یک درخواست باید موفق شود.

در همهٔ پرونده‌ها نسخهٔ اولیه ثابت می‌ماند؛ شمار دقیق رکوردهای مبدا/تصویر، همهٔ فایل‌های فیزیکی و هش آن‌ها با SQL مقایسه می‌شود. فایل موقت `.uploading` نباید باقی بماند. تست مرورگر جدا، هر شش حالت ۴۰۲/۴۰۳/۴۰۹، هر دو مهلت، ثبات شناسه در تکرار و انتظار پیش‌نمایش PDF را بررسی می‌کند. تست ذخیره‌ساز نیز پس از نوشتن بخشی از فایل لغو می‌شود و پاک‌شدن فایل ناقص را می‌سنجد.

## نتیجهٔ اجرا

هر دوازده سناریوی واقعی و پنج تست منتخب مرورگر موفق شدند. ۲۷۸ تست کلاینت و رگرسیون عادی شامل ۷۲۹ تست Domain و دو Architecture موفق بودند؛ ۷۳ تست وابسته به محیط در Domain و یک placeholder سراسری در اجرای عادی skip ماندند. ساخت راه‌حل بدون هشدار و خطا بود. خطای JavaScript، نقض CSP و درخواست خارجی ثبت نشد. گزارش نهایی: `tmp/pdfs/editor-uploads/6900e424cbe745d6bc26edc1167e7aff/uploads-report.json`؛ فایل `cleanup.json` همان اجرا پاک‌سازی شش دیتابیس تازه و عدم استفاده از دیتابیس فعلی را تأیید می‌کند. اشاره‌گر اجرای موفق در `tmp/editor-uploads/latest.json` است.

دو PDF ساختگیِ تک‌صفحه‌ای مورد استفادهٔ سناریوهای بازبینی از نظر متن و نشان پیش‌نویس بررسی و هر دو به تصویر تبدیل و بازبینی شدند؛ renderer و محتوای چاپ تغییر نکرده‌اند. تصویر بازیابی موفقِ درج عکس نیز بازبینی شد. شمارش فقط‌خواندنی SQL پس از تست، صفر دیتابیس QA باقی‌مانده نشان داد.

## محدودیت و استقرار

تغییری در دیتابیس، migration، ساختار ۱۰ سند یا چاپگر v20 نداریم. API مدارک باید پیش از Web و bundle جدید مستقر شود؛ سرور قدیمی شناسهٔ تلاش دوباره را به کار نمی‌برد. API بدون `uploadId` همچنان برای کلاینت‌های قبلی کار می‌کند و رفتار قبلی را دارد.

شناسه و متن محلی فقط در صفحهٔ باز هستند. قبل از بستن/بازآوری، متن ذخیره‌نشده را نگه دارید و وضعیت فایل را در تب تازه بررسی کنید. فایل یکسان با انتخاب تازه عمداً عملیات تازه است؛ حذف خودکار تصاویر استفاده‌نشده یا بازیابی پس از بسته‌شدن مرورگر اضافه نشده است. خرابی SQL/ذخیره‌ساز هنگام ثبت نامشخص، توقف فرایند، قطعی حین همهٔ بخش‌های بدنهٔ HTTP و دستگاه واقعی هنوز نیاز به برش مستقل دارند.
