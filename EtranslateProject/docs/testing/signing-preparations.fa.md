# راهنمای تست آماده‌سازی درخواست امضا

این مرحله فقط برنامه‌ی امضا را ثبت می‌کند. بیانیه‌ها پیشنهادی‌اند و نه امضا، نه رضایت شخص و نه تأیید نوتر محسوب می‌شوند. PDF مرجع همچنان پیش‌نویس بدون امضاست.

## شروع

از پوشه‌ی solution، پروژه را بسازید و AppHost را اجرا کنید:

```powershell
dotnet build ETranslate.slnx
dotnet run --project src/Orchestration/ETranslate.AppHost
```

آدرس Web را از داشبورد باز کنید (معمولاً `https://localhost:7049`؛ پروفایل HTTP ممکن است `http://localhost:5067` باشد). سرویس Trust اکنون دیتابیس جداگانه‌ی `ETranslateTrust` دارد؛ migration در شروع اجرا اعمال می‌شود. همچنان Docker/WSL لازم نیست.

## موارد قابل تست

1. با حساب مالک/مدیر، پرونده‌ی ترجمه را باز کنید؛ ترجمه را ذخیره، PDF بسازید و همان نسخه را در بخش بازبینی به تأیید داخلی برسانید.
2. لینک «آماده‌سازی درخواست امضا در تب جدا» را باز کنید. تا تأیید داخلی PDF جاری، فرم آماده‌سازی ظاهر نمی‌شود.
3. نسخه‌ی ترجمه، دور بازبینی و SHA-256 PDF مرجع را ببینید. دانلود خصوصی همان فایل را می‌دهد؛ این دانلود هنوز امضا ندارد.
4. مترجم فعال را انتخاب کنید. تخصیص مسئول قبلی فقط پیشنهاد اولیه است؛ می‌توانید عضو فعالِ مجاز دیگری را انتخاب کنید.
5. متن پیشنهادی بیانیه و روش `e-İmza` یا `Mobil İmza` را تعیین کنید. هیچ رمز، PIN یا کلید خصوصی وارد نکنید. انتخاب روش در این مرحله به معنای اتصال فعال آن نیست.
6. برای دارالترجمه، مرحله‌ی دوم الزامی است: مالک/مدیر فعال و متن پیشنهادی او. برای فضای مترجم مستقل، فقط مرحله‌ی مترجم وجود دارد. همان فرد، در صورت داشتن نقش مجاز، می‌تواند در هر دو مرحله انتخاب شود.
7. «ثبت آماده‌سازی (بدون امضا)» را بزنید. انتخاب‌ها، متن‌ها و نسخه‌ی PDF در سابقه ثبت و غیرقابل‌ویرایش می‌شوند. ثبت درخواست دوم تا لغو اول رد می‌شود.
8. برای تغییر، دلیل لغو بنویسید و آماده‌سازی را لغو کنید؛ سپس دوباره آماده کنید. سابقه و PDF قدیمی حذف یا بازنویسی نمی‌شوند.
9. تأیید داخلی را در ویرایشگر بازگشایی کنید. درخواست قدیمی حفظ می‌شود ولی اخطار «دیگر به تأیید جاری وصل نیست» می‌گیرد. نسخه‌ی جدید را ذخیره، PDF جدید بسازید و تأیید کنید؛ درخواست قدیمی را لغو و درخواست تازه ایجاد کنید.
10. با حساب مترجم یا Reviewer، سابقه قابل مشاهده است اما فرم آماده‌سازی/لغو ندارید. انتخاب عضو غیرفعال، Reviewer یا عضو فضای دیگر رد می‌شود. نقش سامانه به‌تنهایی صلاحیت قانونی مترجم یا اختیار امضا را ثابت نمی‌کند.
11. متن‌های فارسی/ترکی و متن شبیه HTML را امتحان کنید؛ متن حفظ و امن نمایش داده می‌شود. خطای اعتبارسنجی یا تداخل، متن ارسال‌شده را برای کپی حفظ می‌کند؛ پیش از تازه‌سازی صفحه آن را کپی کنید.
12. دکمه‌ی ارسال برای امضای واقعی غیرفعال است. API ارسال هم برای درخواست آماده‌شده `501` می‌دهد؛ هیچ راه ثبت وضعیت Signed در این مرحله وجود ندارد.

این صفحه ۲۰ درخواست اخیر و حداکثر ۲۰۰ گزینه‌ی عضو فعال را نشان می‌دهد. اگر بررسی فایل در دسترس نباشد، درخواست جدید ثبت نمی‌شود؛ وضعیت تازگی نامشخص است. قطع کامل سرویس Documents ممکن است مانع باز شدن صفحه شود، هرچند API Trust همچنان می‌تواند درخواست شناخته‌شده را لغو کند.

## تست خودکار محلی

با AppHost روشن، در PowerShell 7:

```powershell
./tests/ETranslate.EndToEndTests/Verify-SigningPreparations.ps1
# اگر پنل روی HTTP اجرا شده:
./tests/ETranslate.EndToEndTests/Verify-SigningPreparations.ps1 -WebUrl http://localhost:5067
```

این اسکریپت حساب، فضای کاری و اسناد صرفاً آزمایشی می‌سازد و برای بررسی نگه می‌دارد؛ روی production اجرا نکنید. تست‌های پایه‌ی پنل/تیم را هم اجرا می‌کند. `dotnet test ETranslate.slnx` به‌تنهایی اسکریپت HTTP را اجرا نمی‌کند.

قدم بعدی: انتخاب ارائه‌دهنده‌ی واقعی امضا و تعیین الزامات سند نهایی و بیانیه‌های پذیرفته‌شده. QR، امضای دیجیتال معتبر، نسخه‌ی نهایی و نوتر هنوز پیاده‌سازی نشده‌اند.
