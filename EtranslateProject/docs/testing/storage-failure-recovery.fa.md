# بازیابی خطای ثبت فایل و دیتابیس

تاریخ: ۲۰۲۶-۱۱-۰۴

## چه چیزی اصلاح شد؟

قبلاً اگر ثبت اطلاعات فایل خطا می‌داد، فایل هم حذف می‌شد. اما خطا همیشه به معنای ثبت‌نشدن نیست: ممکن است SQL Server اطلاعات را ثبت کرده باشد و فقط پاسخ موفق گم شده باشد. اکنون این وضعیت برای فایل مبدا، تصویر داخل ترجمه، تصویر قالب، PDF پیش‌نویس و پیش‌نمایش بدون امضای واقعی محافظت می‌شود.

| وضعیت | رفتار جدید |
|---|---|
| خطا پیش از شروع ثبت در دیتابیس | تلاش برای پاک‌سازی فایل همان درخواست |
| ثبت موفق | نگهداری فایل |
| نتیجهٔ نامعلوم پس از شروع ثبت | نگهداری فایل و ثبت هشدار برای بررسی |
| تعارض مشخصِ هم‌زمانی یا شناسهٔ تکراری | بررسی ارجاع به کلید فایل با اتصال مستقل؛ فایل ثبت‌شده حفظ می‌شود |
| در دسترس نبودن بررسی ارجاع | نگهداری فایل |
| خطای پاک‌سازی | ثبت هشدار؛ خطای اصلی یا پاسخ تعارض پنهان نمی‌شود |

این روش ممکن است هنگام نتیجهٔ نامعلوم، فایلِ بدون رکورد را باقی بگذارد. حذف خودکار این فایل‌ها اضافه نشده است؛ اول باید وضعیت ثبت و ارجاع‌های تاریخی روشن شود. ساختار ۱۰، چاپگر v20، مجوزها و اشتراک تغییر نکرده‌اند و migration جدید لازم نیست.

## کاربر چطور بازیابی کند؟

1. اگر نتیجهٔ آپلود مشخص نشد، صفحهٔ دارای متن ذخیره‌نشده را باز نگه دارید.
2. برای مبدا یا تصویر، با همان انتخاب فعلی فایل دوباره تلاش کنید. انتخاب مجدد فایل یا بازکردن صفحهٔ تازه، شناسهٔ عملیات تازه می‌سازد و تضمین جلوگیری از تکرار قبلی را ندارد.
3. اگر PDF قبلاً ثبت شده باشد، درخواست دوبارهٔ همان نسخه و چاپگر، PDF آرشیوشده را برمی‌گرداند.
4. برای تصویر قالب، ابتدا فهرست تصاویر قالب را پس از رفع خطا تازه کنید. این مسیر هنوز شناسهٔ تکرار از کلاینت ندارد؛ آپلود دوبارهٔ بی‌بررسی می‌تواند تصویر دیگری بسازد.
5. اگر فقط دریافت فایل موقتاً خطا می‌دهد، بعد از رفع مشکل ذخیره‌ساز دوباره دریافت کنید. خطای دریافت، رکورد یا فایل آرشیو را حذف نمی‌کند.
6. اگر در این فاصله نسخه، دسترسی یا وضعیت بازبینی تغییر کرده باشد، تلاش دوباره می‌تواند رد شود. رد درخواست را با مجوز نوشتن اشتباه نگیرید و برای نگه‌داشتن متن محلی از راهنمای [بازیابی اتصال](editor-recovery.fa.md) استفاده کنید.

هیچ تلاش خودکاری اضافه نشده است. بسته‌شدن مرورگر همچنان می‌تواند متن ذخیره‌نشده و شناسهٔ انتخاب فایل را از بین ببرد.

## نتیجهٔ تست این قدم

اجرای نهایی: `aa55b559fe0a4d0993dc8cfb71e08dc7`؛ گزارش زیر `tmp/pdfs/storage-failures/<run>/storage-report.json` قرار دارد.

- **۳۲ سناریوی HTTP**: شش حالت خطا برای هر یک از پنج نوع فایل، به‌علاوهٔ دو تعارض واقعی SQL برای مبدا و تصویر.
- **۸ تست مستقل پاک‌سازی**: حفظ فایل در ثبت نامعلوم، حفظ فایل ثبت‌شده در تعارض، نگهداری هنگام شکست بررسی و پنهان‌نشدن خطا در شکست حذف.
- دریافت مجدد و تطابق بایت‌ها و SHA-256 برای همهٔ فایل‌های ثبت‌شده؛ خطای خواندن ذخیره‌ساز و بازیابی آن هم بررسی شد.
- پیش‌نویس و وضعیت بازبینی تغییر ناخواسته نکردند؛ **۲۰ پیام outbox** برای ۲۰ آپلود پذیرفته‌شده ثبت شد.
- پنج فایلِ عمداً بدون رکورد در حالت «خطای تزریق‌شده پیش از SQL، پس از شروع تلاش ثبت» نگهداری شدند. شمار نهایی فایل‌ها دقیقاً برابر ارجاع‌های ثبت‌شده به‌علاوهٔ همین پنج فایل بود؛ فایل موقت `.uploading` باقی نماند.
- شش دیتابیس QA تازه ساخته و پس از آزمون حذف شدند. دیتابیس فعلی محصول استفاده نشد. فایل‌های ساختگی آزمون برای بررسی زیر پوشهٔ موقت باقی می‌مانند.

در این مجموعه SQL Server، migrationها، outbox و ذخیره‌ساز محلی واقعی‌اند. هویت، اشتراک، برنامهٔ امضا و چاپگر، جایگزین آزمایشی دارند. بایت‌های خروجی چاپگر این تست فقط fixture ذخیره‌سازی‌اند و PDF رندرشده یا مدرک معتبر محسوب نمی‌شوند. ارسال outbox در این میزبان غیرفعال است تا شمار پیام‌ها قابل بررسی باشد؛ پیام‌رسانی محصول همچنان SQL است.

خطای پس از ثبت، واقعاً پس از ذخیرهٔ موفق در SQL تزریق می‌شود. خطای duplicate از SQL واقعی گرفته و پس از ثبت تزریق می‌شود؛ این تست، قطع واقعی شبکه در میانهٔ commit یا اجرای واقعی retry ناشی از آن را بازسازی نمی‌کند. SQL Server کاربر خاموش نمی‌شود و مجوز پوشه‌های او تغییر نمی‌کند.

## اجرای دوباره

از ریشهٔ solution، با .NET 10 و SQL Server محلی:

```powershell
pwsh -NoProfile -File ./tests/ETranslate.EndToEndTests/Verify-StorageFailures.ps1 -SqlServer '.\ESIMSSQLSERVER'
```

اسکریپت پروژه را می‌سازد، فقط تست‌های مرتبط را اجرا می‌کند و گزارش مالکیت/پاک‌سازی شش دیتابیس تازه را بررسی می‌کند. حساب اجرا باید اجازهٔ ایجاد و حذف دیتابیس موقت داشته باشد. فایل تنظیمات برنامه عوض نمی‌شود. گزارش `cleanup.json` باید `cleanupSucceeded=true` و `existingDatabasesUsed=false` داشته باشد.

رگرسیون شش سرویس واقعی، جدا با [راه‌انداز آپلود](../../tests/ETranslate.EndToEndTests/Verify-EditorUploads.ps1) اجرا می‌شود؛ جزئیات آن در [راهنمای آپلود](editor-upload-recovery.fa.md) است.

این رگرسیون پس از تغییر هم موفق بود: اجرای `975bde2183024a30b8577748d8137a54` شامل ۱۲ سناریوی آپلود با شش سرویس واقعی و دیتابیس‌های تازه، همراه پنج تست مرورگر و ۲۷۸ تست کلاینت. ساخت پروژه بدون خطا و هشدار بود؛ تست‌های معمول solution نیز ۷۳۷ تست Domain و دو تست معماری را گذراندند. ۷۷ تست اختیاری Domain و یک placeholder قدیمی E2E در اجرای معمول اجرا نمی‌شوند. بررسی فقط‌خواندنی SQL پس از پایان، شمار دیتابیس‌های QA باقی‌مانده را صفر نشان داد.

## بررسی مدیریتی فایل‌های باقی‌مانده

هشدارهای سرویس مدارک شامل کلید داخلی فایل‌اند:

```text
Blob retained after uncertain database outcome; reconcile before deletion
Blob conflict cleanup could not be confirmed
Blob cleanup failed; retained for reconciliation
```

وجود فایل بدون رکورد در یک بررسی لحظه‌ای، به‌تنهایی مجوز حذف نیست. درخواست ممکن است هنوز در حال ثبت باشد و نسخه‌های تاریخی نیز به فایل‌ها ارجاع دارند. کلیدهای فایل و این لاگ‌ها اطلاعات داخلی‌اند و باید در دسترس مدیر مجاز بمانند. در این قدم ابزار حذف دستی یا خودکار معرفی نشده است.

قدم بعدی پیشنهادی، گزارش فقط‌خواندنی تطبیق رکوردها با فایل‌ها، تشخیص فایل مفقود و بررسی هش/سن فایل است. قطع واقعی اتصال SQL، پرشدن دیسک، خرابی فرایند/برق، ذخیره‌ساز مشترک و استقرار همچنان آزمون جدا می‌خواهند.

مبنای طراحی: [ADR 0052](../adr/0052-blob-retention-after-uncertain-database-commit.md) و [توضیح Microsoft دربارهٔ نامعلوم‌بودن نتیجهٔ commit](https://learn.microsoft.com/en-us/ef/core/miscellaneous/connection-resiliency#transaction-commit-failure-and-the-idempotency-issue).
