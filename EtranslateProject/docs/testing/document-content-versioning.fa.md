# راهنمای نسخه‌بندی ساختار محتوای سند

تاریخ: ۲۰۲۶-۱۰-۲۴

آخرین وضعیت ۲۰۲۶-۱۰-۲۷: ذخیرهٔ ادیتور غنی اکنون ساختار ۵ و چاپگر v15 دارد؛ فاصلهٔ قبل/بعد و تورفتگی خط اول به پاراگراف اضافه شده‌اند. ساختارهای ۱ تا ۴ حفظ شده‌اند و شمارهٔ ناشناختهٔ بعدی ۶ است. [راهنمای جاری](editor-paragraph-spacing.fa.md) و [ADR 0036](../adr/0036-versioned-paragraph-spacing-and-first-line-indent.md) را ببینید؛ این گام migration تازه ندارد. گزارش‌های پایین تاریخچهٔ مراحل قبلی‌اند.

آخرین ادامهٔ ۲۰۲۶-۱۰-۲۷: ذخیرهٔ ادیتور غنی اکنون ساختار ۴ و چاپگر v14 دارد؛ بالانویس/زیرنویس به واژگان محتوا اضافه شده‌اند و شمارهٔ ناشناختهٔ بعدی ۵ است. ساختارهای ۱ تا ۳ با قواعد قبلی حفظ شده‌اند. [راهنمای جاری](editor-inline-scripts.fa.md) و [ADR 0034](../adr/0034-versioned-inline-scripts.md) را ببینید؛ این گام migration تازه ندارد. گزارش‌های زیر تاریخچهٔ مراحل قبلی‌اند.

وضعیت جاری ۲۰۲۶-۱۰-۲۷: ساختار ۳ برای تنظیم پاراگراف و چاپگر v13 اضافه شده است؛ ذخیرهٔ صریح ادیتور غنی اکنون نسخهٔ ۳ می‌سازد. ساختارهای ۱ و ۲ بدون تغییر معتبرند و شمارهٔ ناشناختهٔ بعدی ۴ است. [راهنمای پاراگراف](editor-paragraph.fa.md) و [ADR 0033](../adr/0033-versioned-paragraph-layout.md) را ببینید. جدول و رفتارهای زیر گزارش تاریخیِ گام اول‌اند؛ migration تازه‌ای در گام پاراگراف اضافه نشده است.

ادامهٔ ۲۰۲۶-۱۰-۲۷: این گزارش، مرحلهٔ نخستِ نسخه‌بندی با ساختار ۱ را ثبت می‌کند. اکنون ساختار ۲ برای فونت/اندازه/رنگ/هایلایت اضافه شده و شمارهٔ ۲ دیگر ناشناخته نیست؛ [راهنمای تازه](editor-typography.fa.md) و [ADR 0032](../adr/0032-versioned-inline-typography.md) قرارداد جاری را توضیح می‌دهند. نسخهٔ ۱ همچنان سخت‌گیری قبلی را دارد؛ migration تازه یا بازنویسی آرشیو انجام نشده است.

## چه چیزی اضافه شد؟

«نسخهٔ ساختار محتوا» با شمارهٔ ذخیرهٔ پرونده فرق دارد. مثلاً نسخهٔ ذخیرهٔ ۷ می‌تواند همچنان از ساختار محتوای ۱ استفاده کند. موتور ادیتور و نسخهٔ چاپ‌گر PDF هم مستقل‌اند.

در نسخه‌های سند و قالب، دو ستون اختیاری اضافه شده‌اند: `ContentFormat` و `ContentSchemaVersion`. متن JSON داخل `EditorContentJson` همان قالب قبلی را دارد و داخل envelope جدید قرار نگرفته است.

| وضعیت | رفتار |
| --- | --- |
| هر دو مقدار NULL | دادهٔ قدیمی؛ خودکار نسخهٔ ۱ محسوب یا بازنویسی نمی‌شود. بخش قابل‌فهمِ فعلی می‌تواند ویرایش/چاپ شود؛ ساختار ناشناخته حفظ می‌شود. |
| `etranslate.rich-document` و `1` | ساختار فعلی با اعتبارسنجی سخت‌گیرانه؛ متن سادهٔ سند در سرور از محتوا استخراج می‌شود. |
| شناسه یا نسخهٔ دیگر، یا metadata ناقص | تفسیر به نسخهٔ فعلی انجام نمی‌شود؛ نوشتن رد می‌شود و تولید PDF جدید پشتیبانی نمی‌شود. JSON اصلی و PDFهای ذخیره‌شده باقی می‌مانند. |

در HTML، `etranslate.legacy-json / 0` فقط برچسب نمایشی دادهٔ قدیمی است، نه مقداری که در دیتابیس قدیمی backfill شود یا API نوشتن بپذیرد.

ذخیرهٔ کاربر از ادیتور فعلی، یک نسخهٔ جدیدِ معتبر با descriptor نسخهٔ ۱ ایجاد می‌کند؛ نسخهٔ قدیمی تغییر نمی‌کند. کلاینت قدیمی که هر دو فیلد را نمی‌فرستد، descriptor نسخهٔ جاری را به ارث می‌برد و نمی‌تواند آن را حذف کند. ویرایش JSON خام و ویرایش قالب قدیمی، descriptor قبلی را حفظ می‌کند.

## هشدار قبل از اجرای برنامه

**مهاجرت روی SQL Server اجرا نشده است.** فقط فایل آن تولید و مدل/SQL تولیدی بدون اتصال به دیتابیس بررسی شده‌اند.

سرویس Documents از قبل هنگام شروع، migrationهای معوق را خودکار اجرا می‌کند. بنابراین اجرای AppHost یا همین سرویس با باینری جدید، ممکن است migration را روی دیتابیس پیکربندی‌شده اعمال کند. پیش از آن پشتیبان بگیرید، SQL را بررسی و ابتدا روی دیتابیس آزمایشی جدا اجرا کنید. در این قدم AppHost و سرویس‌های محصول اجرا نشده‌اند.

فایل migration: `Persistence/Migrations/20261023223300_AddDocumentContentFormats.cs` در پروژهٔ Documents. عملیات Up فقط چهار ستون nullable و دو constraint اضافه می‌کند؛ متن، قالب تثبیت‌شده، PDF و هش قبلی را UPDATE نمی‌کند. آزمون ساختاری SQL جای اجرای واقعی upgrade روی یک کپی آزمایشی را نمی‌گیرد.

برای دیدن SQL، بدون اجرای آن، از ریشهٔ راه‌حل:

```powershell
dotnet ef migrations script 20261018214412_PinTemplatePerDraftRevision 20261023223300_AddDocumentContentFormats --project src/Services/Documents/ETranslate.Documents.Api --no-build
```

API Documents و Web/BFF را هماهنگ مستقر کنید؛ نوشتن هم‌زمان با باینری قدیمی پس از تولید نسخه‌های دارای descriptor توصیه نمی‌شود. Down ستون‌های metadata را حذف می‌کند؛ بعد از ثبت دادهٔ نسخه‌دار، آن را rollback بی‌خطر فرض نکنید.

## تست‌های خودکار بدون دیتابیس

```powershell
dotnet test ETranslate.slnx --no-restore
./tests/ETranslate.EndToEndTests/Verify-EditorAdapter.ps1
```

فرمان دوم، تست‌های JavaScript و build وب را هم اجرا می‌کند. مرورگر Playwright باید از قبل نصب شده باشد؛ برنامهٔ واقعی، SQL Server یا حساب مشتری لازم نیست. یک سرور موقت با پاسخ ساختگی فقط روی loopback ایجاد و در پایان بسته می‌شود.

پوشش‌ها:

- نگهداری دقیق JSON قبلی، تشخیص metadata ناقص/ناشناخته، جلوگیری از ادعای v1 برای ساختار غیرمجاز و حفظ descriptor در درخواست فاقد metadata؛
- رد downgrade سند مربوط به نسخهٔ آینده، حتی اگر JSON آن شبیه ساختار امروز باشد؛
- استخراج متن ساده در سرور و سقف طول آن؛ تطبیق شناسهٔ سند و شمارهٔ نسخهٔ جاری؛
- انتقال descriptor هنگام اعمال قالب، حفظ descriptor بدنه هنگام تعویض قالب و رد قالب آینده پیش از آپلود؛
- ارسال metadata درست از BFF و رد mode دستکاری‌شده برای سند ناشناخته؛
- یکسان‌بودن HTML آماده‌شده برای محتوای فعلی با برچسب legacy یا v1 و رد نسخهٔ آینده پیش از خروجی؛
- nullable بودن ستون‌ها، سازگاری snapshot و نبود بازنویسی محتوا/آرشیو در SQL تولیدشده، بدون اتصال به سرور؛
- تایپ، جدول، Undo/Redo، ذخیره/خطا/تعارض و قفل نمای فقط‌خواندنی؛ تشخیص metadata قدیمی/فعلی/آینده در مرورگر.

نتیجهٔ اجرای این قدم: ۵۷ تست JavaScript، ۳ سناریوی مرورگر و ۵۳۷ تست عادی دات‌نت (۵۳۵ Domain و ۲ Architecture) پاس شدند؛ ۲۴ تست محیطی Domain و یک placeholder سراسری در اجرای عمومی skip ماندند. ساخت راه‌حل بدون خطا یا هشدار بود. این اعداد به معنی اجرای SQL واقعی یا بررسی تصویری PDF جدید نیستند.

نکتهٔ پایداری تست: در یکی از اجراهای کم‌جزئیات، سناریوی ذخیره/بازخوانی ناموفق شد و جزئیات علت باقی نماند. اجرای مجدد با گزارش کامل و سپس سه تکرار محدودِ متوالی، هر سه سناریو را پاس کردند؛ علت قطعی آن شکست مشخص نشده و رفع‌شده اعلام نمی‌شود. گزارش تکرارها در `tmp/editor-content-regression` است. اسکریپت از این پس TRX را هم در `tmp/editor-adapter` نگه می‌دارد؛ پیش از انتشار، پایداری مرورگر در محیط هدف دوباره بررسی شود.

## تست پس از استقرار در محیط آزمایشی جدا

1. پیش از ارتقا، از JSON، شناسهٔ قالب تثبیت‌شده، فهرست PDF و هش‌های چند سند قدیمی snapshot بگیرید.
2. بعد از migration بررسی کنید اسناد قدیمی هنوز metadata خالی دارند و هیچ‌یک از snapshotهای قبل عوض نشده‌اند.
3. یک پروندهٔ ساختگی را در ادیتور ویرایش و ذخیره کنید. نسخهٔ جدید باید `etranslate.rich-document / 1` داشته باشد؛ نسخهٔ قبل باید عیناً باقی بماند.
4. صفحه را دوباره باز کنید؛ فارسی، ترکی، نیم‌فاصله، قالب و جدول حفظ شوند. درخواست API بدون metadata روی این سند نباید descriptor نسخهٔ ۱ را حذف کند.
5. فقط در پایگاه دادهٔ آزمایشی جدا، fixture نسخهٔ آینده بسازید؛ در برنامهٔ فعلی باید JSON اصلی قابل مشاهده ولی غیرقابل ویرایش باشد و ساخت PDF جدید رد شود. دادهٔ واقعی را برای این تست دستکاری نکنید.
6. PDF ذخیره‌شدهٔ قبل را دانلود و هش آن را مقایسه کنید؛ نباید برای دانلود، از محتوا PDF جدید ساخته شود.
7. قفل بازبینی، نقش‌ها، اشتراک، هم‌زمانی دو تب و دسترسی دارایی‌های خصوصی را دوباره بررسی کنید.

صفحه‌بندی زنده، فونت/رنگ جدید، ورود DOCX، کپی واقعی Word و تبدیل دسته‌ای اسناد در این قدم اضافه نشده‌اند. طراحی: [ADR 0029](../adr/0029-versioned-document-content.md).
