# ADR 0025: Late template changes with immutable per-draft pins

Status: Accepted for the development slice

Date: 2026-10-19

## Decision

Step 5 adds a nullable, restrictive TemplateRevisionId FK to each immutable DocumentDraftRevision. The document-level pin remains a pointer to the latest saved draft. Initial ApplyTemplate keeps its original once-before-first-save semantics and starter text. Normal saves snapshot the current pin. A separate POST `/{documentId}/template-change` requires an exact expected current revision, active tenant-owned target and an editable review state; it copies the exact saved JSON/plain text into a new draft and updates the current pointer. No detach operation or browser-supplied translation body is accepted. A scoped DocumentTemplateChangedV1 event records old/new pins, revision and actor alongside the existing draft-created event in the SQL outbox.

Draft creation, pointer update and outbox commit share the existing transaction and parent CurrentDraftRevision/SQL rowversion concurrency controls. Stale save/review/template races fail with conflict and roll back their inserts. Same-pin no-ops, archived targets and unsaved documents are rejected. Body asset IDs must belong to the destination template; foreign managed images are rejected rather than copied, removed or flattened. Template-independent original source files remain unchanged. Roles, live membership, subscription and antiforgery enforcement are unchanged; the new route is covered by the existing write filter.

Historical PDF generation now resolves template/assets from the requested draft's snapshot, never the document's current pin. Cached archives remain immutable. The scoped GET template endpoint accepts optional `draftRevisionNumber`; absence preserves the old current-pin API. A missing/untemplated historical draft yields 404. Draft response adds nullable TemplateRevisionId, which the Web validates against the returned historical template. History, image URLs and previews therefore follow their own pin. No renderer version bump is needed: rendering of a given immutable draft/template pair is unchanged and new template changes produce new draft IDs/cache keys.

Awaiting/Approved documents remain locked. Authorized correction/withdraw/reopen flows must happen first. Review submission still requires the new current draft/PDF and its current template. Reopened/changed drafts expose no approved signing artifact; old PDFs, review records and proposed signing snapshots are never transferred or rewritten. Existing Trust live-state checks remain authoritative. Historical UI explicitly distinguishes the current document review status from approval of the displayed historical revision.

The Web opens a dedicated DocumentTemplate page in a separate noopener tab, showing current saved revision and readonly/locked status. It never reads or posts another tab's unsaved editor state. Successful change invalidates the old expected revision; a stale editor save preserves typed content and stops with conflict. Unsafe calls are not automatically retried. Users must save text first and refresh the template page; template changes do not promise unsaved-draft recovery.

## Migration and rollout

PinTemplatePerDraftRevision adds the FK column/index and backfills every legacy draft from its document-level pin (including null), justified by the previously enforced immutable once-before-first-save rule. It does not edit translation content, PDFs or source files. Stop all old Documents writers before migrating, take a database/blob backup in important environments and deploy the matching reader/writer version together. Rolling mixed-version writers are unsupported: old binaries cannot populate the new snapshot column. If legacy data was changed outside the application, audit it before applying this inference.

Down refuses to discard snapshots when any historical pin differs from the current document pin; restoring a compatible backup is required instead of destructive rollback after use. Local development startup applies the migration through the existing migration hook. No production migration or deployment is part of this task.

Turkish UI/LTR and final rollout remain steps 6–7. Existing dependency warnings in ADR 0021 are still separate pre-production work. No real signatures, payments, notarization or legal acceptance claims are introduced.

## Verification

Domain/model tests cover exact preservation, nullable/initial/replaced snapshots, inherited pins on later edits, stale/same/foreign/archived rejection and review locks/reopen. Local SQL fixtures exercise save-vs-change and review-vs-change with independent contexts and assert rollback consistency. A separate opt-in migration audit checks legacy pins against a captured predeployment cutoff. HTTP tests cover previously unrendered historical PDFs, existing cache identity/hash, scoped historical reads, body assets, review invalidation, authorization and stale Web forms. Chromium verifies separate-tab behavior, retained unsaved text, conflict handling, correct historical template context and desktop/mobile layout. PDF QA uses synthetic no-template/A/B samples and raster inspection. Existing signing/subscription/order regression also covers expiry denial on the new route. Fixtures are local/synthetic and retained for inspection.

Local verification on 2026-10-19: zero-warning/error build; 498 domain + 2 architecture tests passed, with 17 opt-in domain tests and one placeholder skipped in the normal run; JavaScript 42 passed; EF reports no pending model changes. Legacy backfill audit and SQL race fixture both passed with a cutoff captured before local deployment. Latest late-template suite: 65 additional HTTP checks plus 224 baseline/navigation checks, browser test and SQL race fixture passed (migration audit explicitly skipped when no cutoff supplied). Footer regression: 113 footer + 312 baseline/template checks passed, including per-page PDF semantics. Prior signing/subscription/order regression: 666 HTTP checks + 11 SQL tests passed. Three latest historical/current PDF samples were rasterized and visually inspected, as were desktop/mobile screenshots. New browser assertions use CSP-compatible locator expectations; production CSP is unchanged. Agent-owned local AppHosts are stopped after verification. Only local SQL development migration was applied; no production deployment or user-owned process changes.
