# ADR 0018: Bounded paid access and idempotent internal period allocation

Status: Accepted for the development slice

Date: 2026-10-12

Updates ADR 0017's formerly unbounded Active state. This is not a payment-provider integration.

## Decision

Billing owns configurable plan profiles, paid access bounds and immutable allocation history. Default profiles are `independent-monthly` and `office-monthly`, matched to the corresponding tenant types. Codes, display names, enabled flags and calendar-month counts (1..12) are configured in Billing's `SubscriptionPlans:Plans`; changes require a service restart. No price, currency, tax, checkout, invoice or automatic debit is invented. An authenticated `GET .../subscription/plans` returns enabled profiles eligible for the recorded tenant type, with `purchaseEnabled=false`, `pricingConfigured=false` and UTC period policy. Profile availability is not payment availability.

Trials remain exactly 30 days. A paid month means a Gregorian calendar month calculated in UTC, not 30 days and not the host's local calendar. Allocation keeps the original UTC anchor and cumulative month count: January 31 ends on February 28/29, then a renewal ends on March 31 rather than drifting to March 28. A valid trial's remaining time is preserved by scheduling first paid access immediately after its trial end. Effective reads remain Trialing with plan `trial` until that boundary, then Active with the allocated paid plan. Early renewal extends the existing end from the same anchor; renewal after a gap starts a new anchor at processing time, not an old provider timestamp. An active/scheduled period cannot silently switch plan codes. Canceled/PastDue subscriptions require separate reconciliation before allocation; no refund, dispute, proration or reactivation policy is implemented.

Subscription stores paid start/end, UTC anchor, purchased month count, current paid display name, optional tenant type and optimistic concurrency version. The paid start/end describe the aggregate continuous access window, not an invoice or individual charge cycle. Each `paid_periods` row retains its allocation's plan/name/months, bought segment start/end, source confirmation time, application time, tenant, subscription and source reference. A unique, binary/case-sensitive `(Provider, PaymentReference)` index is global across tenants, and a restrictive subscription FK preserves linked history. Provider/reference are private correlation identifiers, never publicly returned and never themselves treated as evidence of payment.

`PaidPeriodApplicationService.ApplyConfirmedAsync` is **in-process only**. It is not mapped to an HTTP route, message consumer, UI button or CLI activation command. A future trusted adapter must verify provider authenticity, authoritative settled payment identity/time, expected account/order/amount/currency and tenant ownership before calling it; passing a string reference is not verification. Its confirmation time is the stable settlement instant, not webhook delivery time. Amount verification cannot be performed in this slice because pricing/provider integration is absent.

Each attempt uses a dedicated EF context. Existing reference lookup happens before current catalog validation: a matching replay returns the original allocation ID/dates without extending access or requiring a now-disabled profile. Reusing a reference for another tenant, plan or settlement timestamp is rejected. New allocation checks the enabled plan and recorded tenant type, modifies the subscription/version and inserts history in one EF transaction. Unique-index and optimistic-concurrency races retry on fresh contexts up to four attempts; exhausted conflicts require caller reconciliation. Different successful payments append separate segments without losing an extension. Ambiguous database-commit retries can be recovered with the same immutable reference; no business-side payment retry/debit is performed here.

Effective Active requires a coherent, bounded paid window containing the observation time. Active without valid dates/anchor/month count is never an indefinite grant. At exact paid end, reads and write decisions return Expired without waiting for the worker. The V1 write observation has additive optional paid start/end fields; updated consumers require them for Active and check expiry in transit. Trial grants still use trial end, including prepaid trials. New consumers fail closed on older unbounded Active payloads. All consumers should be upgraded before enabling real paid use; these observations remain uncached and are not reusable grant tokens.

The expiration worker now persists elapsed paid as well as trial status, increments version, and handles renewal/version conflicts without overwriting new access or stopping the worker. Read-time status remains authoritative. Cross-service authorization is still not a distributed lock: operations already authorized may finish after expiration.

Overview responses and the Web page show paid plan/name, aggregate bounds, registered month count and remaining paid days, separately from trial metadata. Before a future start, paid remaining days describe the whole prepaid window, excluding remaining trial days. Days round up; exact timestamps are authoritative. Web validates scope, full paid-field coherence, anchor/month-derived end, active bounds and remaining-day calculation. Timestamps are displayed in Istanbul UTC+03:00, while monthly calculations remain UTC. The page creates no receipt or payment claim and still offers no checkout/renew command. GET never extends access.

## Migration and legacy behavior

`AddPaidSubscriptionPeriods` adds nullable paid dates/name/type/anchor, default-zero months/version and the new immutable allocation table/indexes. It does not delete subscriptions/documents, fabricate paid dates, assign a guessed tenant type or create historical payment allocations. New `TenantCreatedV1` consumption records the authoritative tenant type. Existing subscriptions with unknown type remain readable/usable as trials, but paid allocation is blocked until a future trusted Identity-based reconciliation records their type. Legacy Active without a validated paid window loses the former unlimited write grant; no synthetic paid entitlement is inferred. The migration Down removes paid history/columns and must not be run as a data-safe production rollback.

## Verification and limits

Unit tests cover calendar/leap boundaries, trial preservation, immediate boundary transitions, early/late renewal, type/plan/config checks, malformed/unbounded paid grants, expiry in transit and BFF shapes. Opt-in native SQL tests exercise sequential and concurrent duplicate confirmations, concurrent different references, cross-tenant conflicts, no partial allocation on failure, and stale worker protection. The local HTTP suite runs prior signing/enforcement regressions and tests eligible plans, absence of public activation/renew routes, internal service allocation on a newly-created fixture, paid UI, unchanged GET dates and paid expiry/read access.

SQL/HTTP fixtures are synthetic and retained only locally. Their test-only Active states and altered time windows are not purchases, verified financial transactions or a product activation mechanism. Pricing, provider/webhook verification, tenant-type reconciliation, machine identities, trial-abuse rules, refunds/disputes, plan changes/proration, paid notices, invoices, production backups and reconciliation tooling remain future work.
